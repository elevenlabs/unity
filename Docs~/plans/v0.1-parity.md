## #10 — `ConversationOptions` parity

The codegen already emits everything needed
([`OutgoingSocketEvent.g.cs:113`](../../Runtime/Core/Protocol/OutgoingSocketEvent.g.cs#L113)
holds `ConversationInitiationClientData` with `DynamicVariables`,
`ConversationConfigOverride` + nested `Turn` / `Tts` / `Conversation` /
`Agent` / `Prompt`, `SourceInfo`, `UserId`, `CustomLlmExtraBody`,
`ToolMockConfig`). This issue is plumbing.

### Design decisions

**Use the generated types directly, don't author mirrors.** The whole point
of `Codegen~` is that an AsyncAPI re-vendor widens the public surface for
free. The generated namespace is `ElevenLabs.Protocol`; consumers will
write `using ElevenLabs.Protocol;` in the same line they import the
existing `Conversation` types. Mirroring would force a hand-maintained
shim that decays each spec sync.

**Stay explicit-per-field in `BridgedSession.BuildSessionConfig`.** The
existing pattern at
[`BridgedSession.cs:189-202`](../../Runtime/WebGL/Bridged/BridgedSession.cs#L189-L202)
omits null/empty values to satisfy the JS-side union types
(`PublicSessionConfig` rejects an extraneous `signedUrl: null`). A
"serialize the whole record with Newtonsoft" shortcut would lose that
omission discipline — Newtonsoft's `NullValueHandling.Ignore` covers
`null` but not "empty dictionary" or "empty list". Keep adding fields the
same way the existing ones look. Wrap the omission rule in a
`SetIfNonEmpty(JObject, string, JToken?)` helper if call sites get noisy.

**Don't validate field combinations in `ConversationOptions` itself.**
"AgentId XOR SignedUrl XOR ConversationToken" lives in the launcher,
which has full context (e.g., it knows `ConnectionType` and can reject
`ConversationToken` set on WebSocket transport). Putting it on the record
forces it through every code path that constructs options, including
tests.

**Native consumes the typed DTO directly.** `NativeWebSocketConnection`
(see #9 section) builds `ConversationInitiationClientData` and assigns
the override fields from `ConversationOptions` properties; Newtonsoft's
existing `[JsonProperty]` attributes handle wire encoding. No special
serialization path.

### Open question to flag at PR time

The two `Dictionary<string, dynamic>` fields (`DynamicVariables`,
`CustomLlmExtraBody`) come from Modelina's emit for
`additionalProperties: true` schemas. `dynamic` is a deopt path on IL2CPP
(boxing + reflection). For v0.1 we ship the codegen output as-is — if
profiling shows it's hot on mobile, change the generator's preset to emit
`Dictionary<string, JToken>` for these schemas as a v0.1.x patch. Not a
blocker for tag.

## #11 — Method + event parity

This is the open-ended one. The issue body lists 4 method gaps and 12+
event/callback gaps but stops short of partitioning the events by their
data source — that partition is the load-bearing design step, because:

- A **wire-event-driven** callback is purely codegen-and-router work
  (new DTO → new args record → new `Raise*` helper → new public event).
  Lands the moment the spec re-vendor catches up.
- A **derived-state** callback is a logic port from JS into the C#
  router. Independent of codegen.
- A **hybrid** callback (e.g., fires on either a wire event or a derived
  trigger) needs both.

Without the partition, every PR that touches #11 re-litigates "is this a
codegen problem?"

### Recommended structure: a dedicated investigation sub-plan

Created at
[`Docs~/plans/method-event-parity-investigation.md`](./method-event-parity-investigation.md)
— a single load-bearing artifact: a table with one row per JS-SDK
callback **and** one per JS-SDK method (a `kind` column distinguishes
them), columns
`(name, JS source location, classification, blocker if any, proposed C# signature)`.
Built by reading
[`Bridge~/node_modules/@elevenlabs/client/dist/utils/BaseConnection.js`](../../Bridge~/node_modules/@elevenlabs/client/dist/utils/BaseConnection.js)
and the dispatch sites in `BaseConversation.js`. Every subsequent #11 PR
cites a row. When the spec re-vendor (#7) lands new wire types, the table
gets a column flip from "blocked" to "ready" — and the corresponding PR
is mechanical.

The same investigation pass resolves the 5 "uncertain gaps" with
recommendations the user can override:

| Gap | Recommendation | Rationale |
|---|---|---|
| Reconnection / retry | Punt to v0.2; document the explicit non-decision in [`Conversation.cs`](../../Runtime/Core/Conversation.cs) above `EndSessionWithDetails` | JS-SDK behaviour needs tracing; users today get explicit `Disconnected` and can re-call `StartSessionAsync`. Adding auto-retry now risks silent re-connects masking real failures. |
| Session resumption (`ConversationToken`) | Confirm wire flow + add an Edit Mode test pinning the initiation handshake when `ConversationToken` is set; no new code | Field already exists on `ConversationOptions`. If the wire flow is fine, just lock it. |
| Error type hierarchy | Don't mirror JS error classes. Keep `BridgeException` (transport) + `ClientToolException` (user code). Add a `## Error types` section to README in #12 mapping JS errors → C# equivalents | Mirroring a foreign class hierarchy is over-engineering for a different language's idioms. |
| `Status` / `Mode` completeness | Audit JS source for each enum value; add `Status.Reconnecting` IFF reconnection (gap 1) ports | Enums are part of the public surface — get them right before tag. |
| `onDebug` policy | Bridge to `UnityEngine.Debug.Log` behind an off-by-default `ConversationOptions.EnableDebugLogging` flag; no public C# event | An event for debug noise is rarely the right user contract; a flag keeps the surface small. |

## #9 — Native WebSocket transport (Phase 7)

The user's priority: **C# `IConnection` implementation, WebSocket first,
so the SDK works in Editor and on non-WebGL targets**. The issue body
already lists the four component classes; this section names the design
tensions worth pinning before the first PR.

### Sequencing within #9

**Sub-task split rationale.** A single 1500-line "native everything" PR
is unreviewable and impossible to bisect when something regresses. Split
on the layer boundaries that already exist:

- **#9a — `NativeWebSocketConnection` only.** Implements `IConnection`
  against `System.Net.WebSockets.ClientWebSocket`. Edit Mode-testable
  against a Kestrel WebSocket echo server (or a `ClientWebSocket`-paired
  in-memory fake). At this point a Conversation session can `Send`
  outgoing messages and receive incoming wire events; audio gets dropped
  on the floor because no controllers are wired.
- **#9b — `NativeSessionLauncher` + null I/O controllers.** A
  `NullInputController` / `NullOutputController` pair that satisfy the
  interfaces with no-op implementations (no mic, no playback) so
  `Conversation.StartSessionAsync` succeeds in Editor against a real
  agent for **text-only** sessions. This is the first user-observable
  milestone — the SDK runs outside WebGL.
- **#9c — `UnityMicrophoneInput`.** Real mic capture. Unblocks "send
  voice to agent" in Editor + standalone.
- **#9d — `UnityAudioSourceOutput`.** Real playback via `PCMReaderCallback`.
  Unblocks "hear the agent" in Editor + standalone.
- **#9e — IL2CPP `link.xml` + standalone smoke.** Hardens the build for
  shipping; one IL2CPP-built desktop binary opens a session against a
  real agent and prints the reply.

This ordering means **#9a + #9b alone** delivers the headline value
("the SDK works in Editor"); #9c–e are the audio completion path.

### Native-specific design decisions

**URL construction.** Wire endpoint is `wss://api.elevenlabs.io`
(confirmed at
[`Bridge~/node_modules/@elevenlabs/client/dist/utils/WebSocketConnection.js:7`](../../Bridge~/node_modules/@elevenlabs/client/dist/utils/WebSocketConnection.js#L7)).
For `AgentId`: append `/v1/convai/conversation?agent_id=<id>`. For
`SignedUrl`: use verbatim. For `ConversationToken` (WebRTC): native is
WebSocket-only at v0.1; reject with an explicit error if
`ConnectionType == WebRTC`.

**Threading model.** `ClientWebSocket.ReceiveAsync` blocks a background
task. `Conversation` events today are raised from whichever thread fires
them (Bridged impls fire on the JS thread, which is the main thread).
Native must marshal back to the Unity main thread or users will hit
Unity-API-misuse exceptions in their event handlers. Use
`await Awaitable.MainThreadAsync()` inside the read loop before raising
each event. Invisible to the user, matches Bridged behaviour, and
Unity 6's `Awaitable` makes it trivial.

**Read loop lifecycle.** A `CancellationTokenSource` owned by the
connection; `Close()` cancels and awaits the read task. Mirror the
existing `BridgedWebSocketConnection.Close()`'s
"sync-then-disposed" discipline so error-path cleanup works.

**Handshake / format negotiation.** The wire flow is: client sends
`conversation_initiation_client_data` first; server replies with
`conversation_initiation_metadata` carrying the negotiated
`inputFormat` / `outputFormat`. `IConnection.InputFormat` /
`OutputFormat` need to block (`Awaitable<FormatConfig>` or a
"connection's ready" signal) until that metadata arrives, since
`BridgedSession` reads them at the start of the input/output controller
factory calls. Two options:

  - **A.** Make `IConnection.InputFormat` / `OutputFormat` `Awaitable<FormatConfig>` properties (breaking change to the interface — affects Bridged too).
  - **B.** Have `NativeWebSocketConnection` block in its factory method until metadata arrives, so by the time the connection handle is handed out, the properties are populated synchronously.

Option B is non-breaking and matches how
[`WebSocketConnection.create()` resolves on `conversation_initiation_metadata`](../../Bridge~/node_modules/@elevenlabs/client/dist/utils/BaseConnection.js)
in the JS SDK. Pick B; the launcher's `await NativeWebSocketConnection.CreateAsync(...)` is the same shape as the bridged `JsBridge.InvokeFactoryAsync` already used.

**IL2CPP / AOT hardening.** Newtonsoft over the polymorphic
`IncomingSocketEventConverter` plus `OutgoingSocketEvent` subclasses
needs explicit preservation. Add `link.xml` under `Runtime/Native/` that
preserves the entire `ElevenLabs.Protocol.*` namespace. Verify with an
IL2CPP-built standalone (mac is easiest in CI; iOS / Android share the
same IL2CPP linker semantics).

### Audio controller design notes

**`UnityMicrophoneInput`.** `Microphone.Start(deviceName, loop: true, lengthSec: 1, frequency: format.SampleRate)` returns a streaming `AudioClip`; a coroutine or `Awaitable`-loop polls `AudioClip.GetData` at a chunk cadence matching the SDK's expected frame size. `Mute` is a flag the chunk-emit step honours by sending zeros (matches JS-side behaviour — don't pause the mic, since pause/resume has device-quirk surface).

**`UnityAudioSourceOutput`.** A dynamically-allocated `AudioClip` configured with `PCMReaderCallback` reading from a ring buffer; `AudioReceived` events decode base64 → int16 → float and write to the ring. The interrupt/fade should match JS's `webAudioAdapter` behaviour, which crossfades over `resetDurationMs`.

`GetByteFrequencyData` for both: hand-rolled FFT over the live buffer with `System.Numerics.Complex`. Audio visualisers don't need exact parity with Unity's `AudioSource.GetSpectrumData` — just stable monotonic bin values.

### Out of scope for #9 in v0.1

- **WebRTC native transport.** `livekit-client` is JS-only; native WebRTC is a separate package decision (Unity WebRTC package vs. raw libwebrtc P/Invoke). Defer.
- **Per-platform CI matrix.** Per the v0.1 ship decision in
  [`plan-b.md:240-244`](./plan-b.md). One desktop smoke is sufficient.
- **Spatial audio output.** RFC `AudioSink` work; deferred to v0.3.

## What this plan deliberately doesn't decide

- **Public-surface freeze date.** v0.1 is the first tag, so everything is
  "new" — but once tagged, the additions in #10 and #11 are committing to
  init-only properties and public events that survive across versions.
  Each PR should call out the public-API delta in its description so
  the cumulative semver surface stays visible.
- **Versioning the codegen output.** If `Codegen~` ever regenerates a DTO
  with a breaking shape change (e.g., a field renamed upstream), the
  consumer-facing types in `ElevenLabs.Protocol` break too. Out of scope
  here — a v0.x SDK can absorb that churn; the question reopens at v1.

## Open questions

1. **Sample project layout.** UPM `Samples~/` convention is one scene per
   feature, but a single tutorial-style scene that walks through several
   features may be more useful for a game dev's first hour. Decide in #12.
2. **Native upload endpoint URL.** Unknown until the #11 investigation
   confirms whether `/internal/unity` re-exports the upload helper.
3. **Reconnection policy.** This plan recommends "punt to v0.2"; if the
   investigation in #11a finds the JS SDK silently retries, that flips
   the question — auto-retry becomes a parity requirement, not a v0.2
   feature.
